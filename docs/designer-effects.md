# 策划商品效果实验

实验分支 `experiment/designer-effects`，独立 worktree `mhr-designer-effects`。
这是实验实现，不能作为稳定发布承诺。下面“当前验收范围”优先于文末各轮历史记录；历史中的“尚未接线”等描述保留当时事实。

## 当前验收范围（2026-11-14）

单人四种内建效果、网页中文编辑与导出、订单预留／取消、失败与未知交付处理、清理失败阻止下一波、回村恢复及原生保存已验收。新增联机效果事务已接入真实游戏，不再使用业务层 mock 玩家代替原生多人。

同机 Instance1 与独立存档的 Instance3 使用两个模拟 Steam 身份，经原生大厅、承接与出发进入同一任务。已实测：

- 同时争抢全队唯一名额只有一端获得预订；取消确认后另一端可再买，未交付不扣款。
- 从机真实道具入袋0→2，房主真实抽取临时防具；钱包和交付对象分开。
- 第一次允许玩家输入与第一次怪物 update 时，房主攻击字段20，从机攻击10、防御15；全员确认后才放行。
- 同一个原生任务 unique=607647633 内，完成单怪、顺序双怪、同时双怪。顺序第一只死亡不移除强化、不提前发奖励；同时两只确实同时存活。整波结束各端实际字段恢复0/0，各端独立扣款，每波奖励一次。
- 独立 Edge 浏览器经正式网页完成多人异步预订和取消，原钱包不扣款，预留及可用余额随回执更新，无页面脚本异常。
- 第四层房主没有效果订单、从机仅防御15，仍须全员通过准备屏障。从机在原生玩家update里执行一次`setDie`，两端死亡计数0→1；原生复活后从机防御恢复15，房主保持0/0，无二次扣款。随后房主停止，两端正常回村。证据`l4-native-cart.json`、`l4-rebound-*`、`l4-returned-*`；这不是修改猫车计数的模拟。

当前仍不等于官方 Steam 跨电脑、3／4人新效果事务或长局验收。多人故障注入的全组合、进程中断后的运行中重新接管、实际手机网络也未覆盖。旧异常退出尚未归因，不能宣称已经修复。

实现上，DLL0.4.3只提供有界通用信箱；`PeerMailbox`处理原生身份、脚本代数、序号与准确回执。房主`EffectAuthority`冻结报价、效果版本和全队名额；购买者`EffectParticipant`先持久化许可，再调用本地`EffectOrders`，以真实原生回执报告房主。HTTP和网页只发布业务命令，不在HTTP线程调用游戏对象，也不由房主直接写从机钱包。

准备屏障按“任务实例＋逻辑波次token”区分，不以地图重载次数代替波次。实际续波暴露的两类竞争已修正：旧只读状态跨波到达时不把它当新波授权；从机镜像进入新层后旧强化尚未清理时，不接纳新交易或准备确认。旧尸体仍可留在原生列表，准备屏障不能暂停它们或要求它们恢复为活怪。

本地证据在`.local/effects-multiplayer/`（原始失败轮分别存于`round1/`、`round2/`、`round3/`，成功轮有`l2-*`、`l3-*`与`browser-mp-result.json`）。自动化测试曾误将旧价格60写死，实际冻结报价为50；失败断言单独保留，后续按订单报价核算，没有修改运行账本迎合断言。为防原生挂机超时干扰持续自动化，后半轮临时启用20分钟免挂机探针；它不改变人数、战斗结果、效果或账本，不进入发布包，结束时重置移除。

收尾时两端原资源恢复后，分别收到原生保存`status=applied`、`characterSaved=true`（角色槽1与0）的正式回执。已恢复各自实验前配置并重置临时钩子，两端doctor均为Idle、无blocker。最后的协调器优化把每次轮询对订单历史的重复深拷贝改为一次快照＋按ID索引；644条单测、24个Vue渲染场景、类型检查、CLI契约、编译Lua效果与运行回归、跨进程业务协议及3项原生CTest通过。

旧PID87708在02:53的关闭是本轮为更新DLL主动执行，已保留单独操作记录，不能混入非预期退出统计。当前PID113324的ProcDump监控仍在，未见新的未处理异常转储；原19:34非人工退出的根因仍未知。原生任务柜台冷启动初始化的等待修正通过了后续脚本重置后的发任务，但完整新进程第一次发任务仍需独立回归。

## 策划如何配置和交付

1. 游戏进村后打开网页，进入“更多工具 → 策划工作台”，载入游戏配置，再点“商品效果”。
2. 选择或新增商品。选择中文效果，填写价格、效果量、购买阶段、层数、武器和限购。单位与范围跟随效果提供；不支持的阶段不可选。
3. 同组商品共享叠加上限，复制商品也不会另开一组。预览可模拟 PT、武器、已有增益和预留占用；预览不执行 Lua，也不改变下一次抽取结果。
4. 点“导出预设”保存 JSON，交给开发者或测试组织者。接收者从“导入预设”载入、检查差异，再“校验并提交到游戏”。无需让策划编辑 Lua 或 Git。
5. 商品效果规则统一在**下一局**生效。当前局商品、已接受订单的价格、参数和实现不变；页面分别显示本局与草稿，不能把提交成功当成本局已经换值。
6. 想回退时导入之前导出的预设，重新校验提交，再开新局。仅 JSON 回退不能补回已删除的 Lua 实现；开发者更新实现时必须保留匹配版本，缺失的上架效果会阻止提交。

内建效果是固定攻击、防御、发道具和装备抽取。发道具与抽取立即交付核验；攻击、防御针对下一完整波次。游戏道具与装备的效果仍需真实原生读回，配置预览不承诺最终伤害。

## 玩家如何看订单

“当前局”下方的“效果商店与订单”会真实影响本局。顶部、普通商店及效果商店都显示可用余额，并另列预留；预留不扣款，也不能拿去买其他商品。

| 显示 | 含义与可用操作 |
| --- | --- |
| 等待生效 · 可取消 | 尚未开战，可取消并释放 PT、名额 |
| 已锁定 · 等待场地就绪 | 已选波，不能取消；仍未扣款 |
| 生效中 | 原生读回已满足承诺，并已扣款 |
| 确认未交付 | 不扣款；确认放弃后可重新检查准备 |
| 交付待核实 | 保留预留，不重试、不强制退款；点“只读核实交付” |
| 恢复待办 | 已有修改尚未核实移除；阻止下一波，允许核验清理或停止 |
| 恢复后封存 | 原资源恢复并保存后结清恢复义务；不改写原交付历史 |

初次入场允许场地和角色初始化，效果未核验前暂停怪物更新与战斗操作。失败时处理订单后点“重新核验并继续”，也可以停止本局。顺序双怪按一个完整波次处理，第一只死后不清除增益；猫车后等待原生角色恢复再重新绑定，不重复扣款。清波时读回移除结果，不能只把状态改成“结束”。

未知道具交付不能凭后来背包数量碰巧匹配就补扣钱；原角色对象变化也不能证明旧属性订单已交付。确实无法判断时，安全停止、恢复原物资及装备，再执行“原生保存并确认恢复”。保存只核验恢复，不伪造原购买成功。

原商店攻击／防御强化与效果商店同类强化互斥，避免两套逻辑同时写同一字段。任何一侧交易尚待核实时，不从另一侧继续购买来改变核实依据。当前新效果商品仍限定单人；原有多人商店能力与新效果的多人事务不是同一验收项。

## 已实现的入口

- 策划工作台 → 商品效果：中文效果目录、参数说明与范围、价格、上架/下架、共享组上限、限购、层段、购买阶段、武器限制与互斥组。
- 规则预览复用真实订单资格判断，可模拟武器、阶段、可用 PT、组内已生效／预留占用、限购次数及互斥组。不执行 Lua、不调用抽取 RNG。
- 新效果商品配置全部下一局生效；编辑器对照本局商品和草稿，运行快照标记已有待用的下一局规则。原有商店的调价策略不变。
- 当前局 → 效果商店与订单：可用/预留 PT、冻结报价、取消、执行与清理回执、未知结果核实。
- `data/effect_catalog.json` 列出 Lua 模块，实际部署于 `reframework/data/rogue_effects/`。
  模块声明 definition/check/apply/inspect/remove，使用显式原生能力适配器；不从 HTTP 工作线程执行。
  已接受订单保留内容摘要及参数；刷新目录不替换进程中已冻结的实现。
- `effectShop` 配置中的商品绑定效果 ID/版本与参数，组规则按稳定的效果组 ID 共享，复制商品不绕过组上限。
- 立即交付核验后结算；下一波效果预留 PT，开战锁定后核验属性并结算。
- 订单持久化由已有原子写盘器处理，白名单新增 `mhw_rogue_effect_orders.json`；源码可提交，构建 DLL 不提交。
- 效果目录和四个内建脚本已加入显式部署／发布资产清单，放在 data/rogue_effects；实验探针和示例配置不自动进入发布包。
- 缺失实现、参数版本不匹配的商品逐项显示原因；上架商品阻止提交，下架商品可保留旧记录，不影响其他有效商品显示。

## 猫车后的绑定、恢复与清理（2026-11-13）

实机失败证据 `cart-native-result-2.json`：原生猫车计数 0→1，字段经历 30/15→0/0→30/15（死亡动画中）→0/0（复活时）。旧实现过早重绑，复活的第二次原生重置清掉了增益。PT 没重复扣，但效果保留不符合约定。

修复后：死亡或载入期间订单进入 `suspended`（等待复活后恢复），不写入；本机角色 `getDieCount()` 与实例身份用于识别重建，不使用可增减的共享猫车余额。复活后再按原购买顺序重绑；若整组值仍保留，只更新核验证据，不重复添加。结束时按相反顺序清理。没有真实玩家对象时不能据此断言旧对象已销毁。

`cart-fixed-result.json` 和对应快照验证：
