# 联机运行协议与验收范围

入场沿用 MultiplayerEntry 的 Steam lobby 任务描述和全员 ACK，经原生任务看板入队。入场任务号900103，正常包默认接入，不依赖 DebugMode。各端先完成个人装备/背包备份、零物资与初始套装准备，进入 Preparing 阶段用初始 PT 购物。首波与后续波次共用奖励和人数倍率规则，首波不再是零分校准波。

## 职责

- 房主 RunSession 生成三选一，观察原生怪物死亡/捕获和全员集结，推进层数，计算累计奖励与共享猫车。
- 队友 RunSession 读取真实场景，但不独立推进状态、不选波、不生成随机候选、不触发原生任务完成。
- 每人钱包独立。房主传递累计已发 PT，队友按增量入账；重复/乱序帧不能重复发钱，也不会覆盖个人购物支出。道具写入各自原生背包并读回。
- 倍率人数使用入场锁定的真实成员数，优先于离线 mock 名单，也不随猫车或加载时短暂缺失的玩家实体变化。日志 `multiplayerRun.fixedPartySize` 是该固定人数；原生实际人数仍单独观察。
- 从承接切入局内协议时继续沿用全员确认过的名册，不重新吸收大厅当前成员。准备/承接后迟到的成员不自动获得本局资格；运行协调器发现实际名册变化会停止，等待恢复后重新准备。
- 房主购买共享猫车恢复；队友同步该恢复一次并读回原生死亡计数。攻击/防御写入本机 PlayerData；会心在 PlayerQuestBase.calcCriticalRate 完成后，只调整本机 actor 当次攻击的运行时 CriticalRate，不改共享武器表。当前原生代码内联了 getAdjustCriticalRate，钩住该 getter 不会覆盖真实伤害路径。

## 出怪确认屏障

所有端都运行原生加载前置登记。房主选择当前空槽、分配原生 EnemySetInfo，发布 ticket：波次 token、波内序号、怪种、任务槽、EmSetId、UID。队友按同一个槽登记，逐项比对 id/UID 后 ACK。确认前不写入 RequestLoad 阶段；不一致立即停止，不能直接改 UID 伪造一致。

房主收齐固定队伍的登记 ACK 后发布 commit，本机及队友才启动原生 RequestLoad → LoadWait → SyncLoadWait → CreateEnemy。下一只 ticket 必须等所有端确认前一只已启动，防止较慢客户端漏掉被覆盖的 commit。Sequential 额外等待上一只死亡；Simultaneous 允许前一只继续存活。战斗实体和伤害仍由 Rise 的原生网络处理。

## 状态通道

复用 DLL 已有 steam_plan / steam_ack，不新增 DLL 接口。入场 schema3 信封携带随机种子、固定队伍、完整规则摘要；进入任务后，同一 lobby data 改发 v4 状态帧，MultiplayerEntry 停止轮询，由 MultiplayerRun 接管。帧包含房间、owner、运行session、完整配置 SHA256、递增sequence、阶段、层数、波次、候选、累计奖励、猫车和出怪 ticket。紧凑波次编码使每个值在2048字节内。每秒发布一次，未逐帧写日志。

队伍和房主固定。配置摘要用递归排序编码，不依赖 Lua 中不存在的 JSON/Date/Array 全局。房主身份、队伍变化、配置不一致、原生 ID 不一致、90秒出怪确认超时或120秒状态超时会停止本局。客机购物未决时不确认可进入下一波。联机不自动降级为各自重进任务。

## 已有证据与剩余验证

TypeScript 双端协议测试和编译后 Lua5.4 双端测试覆盖了主从选波、登记/commit/启动、重复与旧帧、个人余额、配置差异、掉队、超时及共享猫车恢复。原生登记测试验证确认前不启动加载、客机不自行分配、ID不一致不启动。

此前真实在线房主本机测试证明了同一任务内四层、Single/Sequential/Simultaneous、奖励和真实道具购买。2026-11-04 另在本机两个真实引擎、不同模拟 Steam 身份下完成原生任务10101共同入场：客机看板可见、接取、准备、房主出发，两端同任务 unique/session、isPlayQuest=true、人数2且各有两个原生玩家实体。详见[单机双客户端测试](local-multiplayer-testing.md)。随后在相同本地模拟环境中，用任务900103完成入场波及Single、Sequential、Simultaneous连续四波：两端原生UID与同时双怪最大HP一致，原生讨伐复制、全员集结、奖励80/123/141PT各发一次，双方真实道具购买与个人余额隔离均通过。普通武器伤害、捕获与恢复的后续验证见本文11月9日记录；不同电脑官方Steam/公网仍未验收。2026-11-05 双端共享猫车计数、房主付费恢复及 stop 后自动结算回村通过。R12/R13曾被写成三猫失败通过，但当时未核实原生结束原因，现撤回这一结论；有效三猫失败证据以本文11月8日修正及双端 Failed=4 记录为准。原生结束调用时机与消息生命周期修复仍有独立的崩溃排查证据，不能据此推断任务结束类型。

按[两人测试说明](tester-guide.md)验证，日志 state 的 multiplayerRun 保留角色、固定队伍确认状态、ticket 和错误原因；支持下载应包含双方当时的数据。网页显示 live 只表示本端协调器工作，不表示全部联机能力已验收。


## ACK 活性与兼容性（2026-11-04）

运行协议为 v4（R4 ACK），当前入场规则摘要包含 runtimeProtocol=7，旧版客户端不能混入；配置代号参与运行 ACK，见下文配置维护。新版包含效果商品的独立业务信箱和全员原生准备屏障；其验收范围另见 [效果实验记录](designer-effects.md)。
房主每秒发布递增序号，从机 ACK 必须回显该序号；只有回显最近 15 秒内发布且比上次更新的
序号才证明活性。反复读取缓存 ACK、过期序号或未发布的未来序号均不续期。
15 秒失联后阻止房主选波/生成确认，全员就绪持续中断超过 120 秒停局。

`python scripts/check-multiplayer-process.py` 已通过两个独立 OS 进程、实际编译 Lua 和

## 真实双端测试后的入场门槛

承接完成前继续由MultiplayerEntry驱动原生柜台，不能仅凭activeQuest切入运行协议；必须确认承接队列结束且isPlayQuest=true。原生play状态仍早于玩家坐标完成迁移，RunSession还会等待isEndLoadQuest和任务已运行至少1秒后才记录集结点。过滤村庄玩家实体与非有限位置。否则会把村庄坐标记为斗技场集结点，造成清波后永久无法继续。

2026-11-04最终双端证据在本地 `docs/evidence/2026-11-04-multiplayer-roguelike/`，见README与verification-summary.json；按仓库约定用`rg --no-ignore-vcs`查询，不把这些日志和探针放入发布包。


## 新局与配置维护

一局结束后双方先等原生结算、保存及实际回村。恢复个人装备和道具袋完成后会自动退役旧协调器、清除旧大厅计划/ACK、轮换桥会话并回到 Idle；无需 Reset scripts，可在同一大厅重新准备。网页保留上一局结算摘要。个人开局装备、奖池、增益和节奏从本局已确认的配置刷新，内部联机任务号不会覆盖用户的单人任务配置。扩展新能力与验证层次见[开发维护](development.md#扩展功能的边界)。

局内调参由房主在 Selecting、全员集结且交易完成时提交。独立配置通道按 prepare → commit → release → done 同步：全队校验模式和本机装备目录，再分别应用和保存，房主收到固定名册全部确认后解除屏障。期间禁购、禁选波；个人钱包、购买记录、已发掉落及当前波次保留。价格用于后续交易，曲线/奖励/怪池在下一次生成选择时使用，已经展示的选项不会重算。起始 PT、猫车上限、初始装备、抽取池、增益数值、猫车恢复规则和流程节奏仍冻结到下一局，语义与单人一致。队友可编辑/导出草稿，但不能独立热改本局。

需要 DLL 0.4.2；入场规则协议升到6，旧版本应在准备时拒绝混用。配置最多64 KiB，经完整摘要校验后处理；缺块不应用、旧会话/旧提案确认不生效。准备阶段校验被拒时保留旧规则；部分提交失败则停止本局并恢复，不能按混合数值继续战斗。各端以独立原子恢复记录保护旧配置，损坏或无法恢复时保留文件并阻止开局与配置覆盖；启动只保留原装备恢复能力，不把默认配置作为可游玩方案。文件锁解除后在安全村庄自动重试，不要求 Reset。未完成事务不支持带战斗进度续传，恢复后需重新准备。

本机双真实引擎已验证同一任务内改价、队友按新价购买、个人余额隔离、后续生成倍率与双方原生 HP 一致。该轮随后取得三次怪物攻击猫车、Failed=4、无 Success=3、原生保存及完整装备/道具袋恢复证据。随后构建727bdab补齐本机三/四端配置实机样本，见本文末记录；这仍不等同官方 Steam 跨电脑验收。


## 2026-11-08：原生失败与首波规则修正

先前“计数到三猫并返回村庄”的证据不足以证明任务失败：首波目标已满足时，先释放完成拦截再请求失败，会被成功判定抢先结算。现在先锁定结束任务实例，再从 QuestManager.update 的原生上下文请求 setQuestFail，期间继续拦截 setQuestClear / setQuestClearSub。验收必须记录 Failed=4，并且结算、保存期间不能切成 Success=3。

本轮本地双引擎复测：首波讨伐得80 PT → 同场第二波 → 怪物真实攻击造成三次猫车 → 双方 Failed=4 → 保存回村 → 自动恢复 Idle → 不重载脚本直接再准备、购物并共同进入同时双怪任务。开局个人套装、回复药与装备抽取也已验证。临时装备每次新增独立条目，即使拥有同款原装备也不复用强化、珠子；局末按箱位及身份核验后只清理本局条目。

证据在本地 docs/evidence/2026-11-08-multiplayer-completion/。与该成功路径分开记录的事件：一次人工原生失败探针、几次传送观察错误、大厅失联。未把这些事件记作三猫完整通过。

清波补给掉落在每位玩家本机独立抽取，队友以新的累计 PT 奖励触发一次，收到重复帧不会重抽。发货等待本机原生怪物全部死亡/捕获，满袋或部分发货只记结果、不扣 PT、不自动重发。SupplyDrops 的概率和道具权重可在策划编辑器调整；旧自定义配置未设置该项时仍关闭，需要全队同步启用。

## 2026-11-09：队友停止与重复结算

队友主动停止或本机运行异常时，先锁定当前任务号/unique 的失败完成拦截，再通过当前 lobby/session 的结束通知请求房主处理；房主负责原生失败，队友不自行结束全队任务。发送失败按秒重试，原生已经结束或实例改变即停止发送。旧会话的 stop 也不能结束同任务号的新实例。当前通知复用 R4ERR 并携带 stop/fault 类型；队友正常停止由房主转成 Finished，真正同步异常才进入 Fault。已补通知类型的协议回归。

本机双真实引擎复测：首波清波后L2队友停止→双端Failed4→保存回村→个人恢复→不Reset下一局；下一局L2受怪物攻击造成三次猫车，再次Failed4并恢复。未把任务完成Success3当作失败。最终构建还分别验证房主停止、队友停止后连续回村重开；NativeUi跨业务会话复用已安装钩子，轮换bridge/token并清空旧输入，第二次结算不再累加生产UI钩子。按需测试输入脚本自己的钩子不属于玩家包。

证据位于本地 `docs/evidence/2026-11-09-multiplayer-abort/`。剩余单人/多人对齐门槛和逐项实现方式见[策划对照](design-coverage.md#单人与多人对齐交付门槛)，不是对不同电脑官方Steam、所有怪池和无限长局的完成声明。

结束原因记录新增复测（构建0202ea0）：同一双引擎任务-924208418由怪物实际造成三猫，双方Play2/0→1→2→3→Failed4，无Success3；新摘要在回村后仍保留本机failed/deaths3及原任务unique。随后同厅、同Lua代际、无Reset进入下一任务-543385035，队友主动停止，双方记录stopped/failed/deaths0，未沿用上一局三猫结果。两条路径都完成原生保存，完整装备属性、穿戴、普通/弹药袋及容量与开局前逐字段一致，最终Idle且恢复待办清空。证据在本地 `docs/evidence/2026-11-09-ending-parity/`；本次不新增三/四端配置或官方跨电脑结论。


恢复记录现绑定原生角色槽及 GuildCardID，错角色或损坏文件不会被当作无记录覆盖。进程标识跨 Reset 稳定、冷启动轮换，原生对象地址不能跨进程作删除凭据。跨进程临时装备回收必须先核验完整属性与归属；旧格式无法证明的记录仍保持待办，完整恢复范围见[策划对照](design-coverage.md#1-恢复记录的持久身份与异常恢复)。所有 applied/queued 回执发布前先更新业务快照，CLI 紧接查询不再看到命令执行前的开局/停止状态。

## 恢复与保存的边界（2026-11-09）

三猫失败必须独立验收，普通完成或手动停止回村不能替代。11月9日重新核对的双引擎任务 unique -1863885984：由怪物攻击造成三次猫车，两端均记录 Play/0→1→2→3→Failed/3→None，无 Success；随后自动保存、恢复原装备和非空普通/弹药背包，恢复待办清空。未 Reset 即共同进入下一实例1398221267。下一实例的 stop 仅作测试清理，与前场三猫分开。原始记录在本地 `docs/evidence/2026-11-09-real-cats-clean/`。

抽取配置和原生发放入口均拒绝缺失/越界部位编码的防具 ID，并检查原生 ID 范围与装备数据实际存在；未知、超过32位或目录不可读的 ID 不进入装备箱。开局在写记录、卸装与发放前先检查完整套装和指定武器；网页配置失败时不改变原方案或版本。目录存在不代表所有系列的玩法均已实机认证，策划仍须选用已核对的游戏装备。

“内存已恢复”不等于“原生角色存档已保存原装”。恢复器现在保留装备和道具袋记录，直到观察到新一次原生角色保存、对应角色槽成功，并再次核对完整原装备箱指纹、穿戴栏和物资，才退役记录。不会调用强制保存入口；自动保存关闭或错过保存时，网页提示在原生菜单正常保存。

临时件使用预留空槽及完整属性指纹，跨进程和同进程重新加载都重新核对活数据。缺少预期物资备份、记录损坏、归属或原装备变化时保持待办，不按同款ID猜测删除。单人reentry层间保存不触发整局回收，个人准备中的袋隔离失败会回滚并拒绝ACK。

最终双引擎任务900103 / unique -1395269277：个人准备、购买/抽取、首波80PT、怪物攻击三猫，双方轨迹Play2/0→1→2→3→Failed4→None0，无Success3；双方原生保存成功、原装精确恢复，并不Reset进入下一场Combat。归档第三猫后的原生保存镜像，再以inactive恢复记录冷启动双方，完整装备、穿戴、非空普通物资与弹药一致。证据在本地 `docs/evidence/2026-11-09-recovery-save/`，与单人停止保存专项及下一场清理stop明确分开。

这些证据来自同机双引擎和独立模拟Steam身份。恢复记录的临时文件替换与进程中断测试现已补齐；硬件断电不在该测试范围。手动捕获流程、跨电脑官方Steam与长局仍分别保留验收门槛，见[策划对照](design-coverage.md)。
